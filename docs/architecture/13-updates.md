# 13. In-app updates

The Store package updates itself from the Microsoft Store, but Windows can't switch a running app to a new version: its own updater downloads and stages the update, then fails with `0x80073D02` while the app runs, and doesn't retry when it closes. TextTemplateManager runs in the tray all day, so it triggers the switch itself. Everything lives in `Services/Updates`; the UI parts are `MainPage.Updates.cs` (the notice), the Updates section of `GeneralSettingsPage` and the tray menu.

## How Windows behaves (measured)

Measured on the developer's PCs with the Store package and on a test VM with sideloaded packages (October 2026):

- An update is **staged** (downloaded next to the installed version), then **registered** (the switch). Only the register needs the app closed.
- Registering the staged package by family name with `ForceTargetApplicationShutdown` makes Windows close the app, switch, and, when the app called `RegisterApplicationRestart`, start the new version right away with the given command line. No helper and no extra capability are needed.
- A failed register leaves the update waiting; the next start **from the shell** (Start menu, logon task) with the app closed applies it. `AppInstance.Restart` doesn't.
- `uap17:UpdateWhileInUse="defer"` doesn't queue anything: it only makes Windows ignore force-close requests, so it isn't used.

## Classes

![Update classes](diagrams/class-services.svg)

- **`UpdateService`**: the updater's logic and state (`UpdateStatus`, `UpdateStage`), free of UI types so the tests drive it with stand-ins. Checks every six hours from the last check (`UpdateCheckHistory`, `update-checks.txt`, so it survives restarts), at the earliest two minutes after the start, first looks for a version Windows already staged (`IPackageSwitcher.FindStaged`, without asking the Store), downloads right away when the source allows it or the user asked (**Check for updates**: through the consent dialog when the Store can't download on its own), and runs the switch. With the user's **Check for and download updates automatically** off (`AppSettings.NoAutomaticUpdates`, `UpdateService.CheckAutomatically`) only **Check for updates** checks, and there is no idle install and no install on quit (`InstallOnQuit`). `Changed` may fire on any thread; `App` marshals it to the UI.
- **`IUpdateSource`**: where updates come from. `StoreUpdateSource` uses `StoreContext` (`GetAppAndOptionalStorePackageUpdatesAsync`, `TrySilentDownloadStorePackageUpdatesAsync` to stage without installing, `RequestDownloadStorePackageUpdatesAsync` for the Store's consent dialog). The Store never names the new version: each `StorePackageUpdate.Package` is the **installed** package, so `StoreUpdateSource` offers an `UpdateOffer` without a version as soon as the list isn't empty (reading the version from it made 2.2.0 report "up to date" while 2.2.1 was out). Whether the update is downloaded comes from the Store's queue item for the app (`GetAssociatedStoreQueueItemsAsync`): `PausedReadyToInstall` once it's staged. The download calls report Completed after about a second, before anything is downloaded, so the source waits on the queue item (every 2 s, at most 30 min, with its progress). An update check puts the queue item back to `Paused` although the package stays staged, so the queue is read before each check and remembered (`IsDownloadedAsync`). Measured on the Store's 2.2.0 → 2.2.1 on 2026-10-21; no package list available without admin rights shows a staged package. With automatic Store updates off the queue item can sit in `Paused` (BlockedOnUser) for good; the source stops waiting after two minutes of it. A version staged outside the queue (Windows Update) never shows there: see `AppxStageLog`. `FileUpdateSource` is the test source for sideloaded builds: the newest `.msix` of the app in the folder `TTM_UPDATE_SOURCE` names, staged with `PackageManager.StagePackageAsync`; a file `consent-only` in that folder makes it behave like a Store under the "no automatic updates" policy, and `consent-fails` makes its consent download fail. The Store package never uses it.
- **`IPackageSwitcher`** / **`PackageSwitcher`**: `IsStaged` (the staged package's folder next to the installed one, for offers with a version), `FindStaged` (the newest version above the running one that `AppxStageLog` names and `IsStaged` confirms), `RegisterRestart` (`RegisterApplicationRestart` with no-crash/no-hang/no-reboot flags, so only an update restarts the app), `StartWatchdog`, `SwitchAsync` (the forced register).
- **`UpdatePolicy`**: `HKLM\SOFTWARE\Policies\Marflow Software\TextTemplateManager` (`InAppUpdates` 0/1/2, `AllowUpdateDespiteStorePolicy`, `AutomaticUpdates`, `IdleInstall`) and the Store's `AutoDownload` = 4. The policy is read again before every check and, through `UpdateService.RefreshPolicyForSwitch`, right before every switch (Restart to update, idle install, quit), so a policy set while an update is ready takes the ready state away. With `InAppUpdates` = 1 an update Windows has already staged stays a notice. `AutomaticUpdates` 0/1 overrides the user's automatic-updates switch (`UpdateService.ChecksAutomatically`). `UpdatesDespiteStorePolicy`: the Store policy is on and the administrator allows TTM's own download anyway (`AvailableStatus.CanDownload`): `RouteFor` takes the request route (`RequestDownloadAsync`, over `UpdateService.OwnerWindow` when no window is passed) for the user's Download and Check for updates, and on its own with automatic updates on. On a PC with `AutoDownload` = 4 and without the Store app it resumed the Store's waiting queue item (BlockedOnUser) without a dialog (2026-10-22). The winget route of 2.2 to 2.3.2 couldn't work, as winget's `msstore` source lists the app's version as *Unknown* and answers "No newer package versions" (`0x8A15002B`, seen 2026-10-21). A failed download is `Failed` with the error code; **Try again** (and **Check for updates**) download an update already known (`_offer`, stage Available or Failed) without a new check, so the Store's 30-minute window doesn't block them. Seen 2026-10-22: `0x80244007` from the Store's download right after a release, gone on the next try. When the request route reports done but nothing gets staged under the policy, the notice adds `UpdateService.WindowsUpdateHint`. Settings shows a note under the automatic-updates switch while the Store policy is on.
- **`UpdateAttempt`**: `update-attempt.json` in the data folder, written right before a switch; the next start compares the running version with it (`EvaluateStartup`). After two failed tries for one version only the manual steps are shown.
- **`UpdateCheckHistory`**: the times of TTM's own checks in the last 24 hours. The Store answers an app at most one check per 30 minutes and ten per 24 hours and otherwise repeats its last answer (documented under "Detection frequency" of `GetAppAndOptionalStorePackageUpdatesAsync`; seen as "Scan not allowed inside interval" in the Store log, with every caller of the app's identity counted). `NextAllowed` tells `CheckAsync` whether a check would get a real answer: automatic checks are skipped inside the limits, and **Check for updates** then says when the next one is possible instead of reporting a stale "up to date".
- **`StoreScanLog`**: checks by other callers (the Store app's product page, winget, diagnostics) aren't in TTM's history. When the Store returns no update, `StoreUpdateSource` reads the Store's Operational event log (`System.Diagnostics.EventLog`, no admin rights needed) for a refusal logged since the check started: "Scan not allowed inside interval" or "Online scan not allowed due to cooldown period" for TTM's package family, with the app's scan times ("Current last scan time cache"). It sets `RefusedUntil` from those times with the same limits (the Store's own log also shows `OneSettingsOnlineScanCooldown = 1800` seconds); `UpdateService` then says the Store didn't check and when it will, logs it, doesn't count it as a check, and waits until then. The log text isn't documented: when it isn't found or reads differently, the empty answer counts as "up to date" as before.
- **`AppxStageLog`**: the versions Windows staged, from the AppX deployment log (`Microsoft-Windows-AppXDeploymentServer/Operational`, events 400/478 "Deployment Stage operation … on Package <Name>_<Version>_<Arch>__<PublisherId> … finished successfully", readable without admin rights, about 0.1 s). Needed because Windows Update stages Store app updates too, also with automatic Store updates off and without the Store app (seen 2026-10-21 on 2.3.1 → 2.3.2, caller `MoUsoCoreWorker`): its install fails while the app runs (`0x80073D02`), the Store's queue item never shows it, and Windows installs it only at the next start. The log names the version, which the Store never does.
- **`UpdateLog`**: `update.log` next to the crash log, every step including checks without an update, trimmed at 256 KB. A failed check, download or switch shows the user only the error code and where it came from (`IUpdateSource.DisplayName`, e.g. "Microsoft Store, error 0x80244007"); the log gets the code with the original message (`UpdateError.Describe`, `DownloadResult.Detail`, `SwitchFailure.Detail`). Plain reasons without a code (low battery, Wi-Fi) are shown as they are.
- **`IdleInstall`**: when idle install may switch (`ShouldInstall`) and the time since the last input.

## Stages

![Update stages](diagrams/state-update.svg)

The notice above the panes (`UpdateBar`) shows Downloading (with progress), Ready (**Restart to update**), Available with **Download** (automatic Store updates are off: the Store's consent dialog, or after it failed the hint to Windows Update), Available without a button (notice-only policy, or the Store policy without the admin's permission), Failed (**Try again**) and the manual steps. Closing it hides it until the stage or version changes. Settings ▸ General ▸ Updates shows the same stage as text and turns its button into the notice's action (Check for updates, Download, Try again, Restart to update), so nothing needs the main window. The tray menu has Restart to update while an update is ready (the menu is rebuilt with or without the item, as the tray's native popup menu ignores an item's `Visibility`; clicked when nothing is ready, it opens the window), and a tray notice says so once per version when the window is hidden.

## The switch

![Restart to update](diagrams/seq-update.svg)

`App.InstallUpdateAsync` handles unsaved edits like a quit (Restart to update only; the idle install runs only without them), stops the hotkey and the connector, and runs `PersistPendingAsync` (pending saves, registered flushes, a recent backup). `UpdateService.SwitchAsync` then writes the attempt, registers the restart (`--updated`, or `--updated-idle` for the idle install), starts the watchdog and calls the forced register. On success the process is ended by Windows; when the call returns, the switch didn't happen, the app turns its input back on and shows the reason.

- **Watchdog**: a one-time task in the user's Task Scheduler (`TextTemplateManager update watchdog`, from `update-watchdog.xml` and `update-watchdog.ps1` in the data folder). Two minutes after the switch (Windows' own restart took 10 to 110 seconds on the test VM) it starts the app through the shell if it isn't running, which also applies a switch still waiting, notes what it did in `update.log` and deletes itself. A scheduled task runs outside the package; a child process started with the desktop-app breakaway attribute was still ended with the app at the switch on the test VM.
- **60 seconds**: `RegisterApplicationRestart` only takes effect once the process has run for 60 seconds, so `InstallUpdateAsync` waits until it has run 65.
- **Restart arguments**: `--updated` opens the window, and What's new shows as after any update (`StartupGreeting`). `--updated-idle` (idle install) does the same; it only tells the two apart in the log.
- **Quitting with an update ready** (`ExitAsync`, only with automatic updates on) switches without a restart (`UnregisterApplicationRestart` first), so the next start is the new version.

## Idle install

A dispatcher timer checks every minute: update ready, allowed (user setting `IdleInstall`, off by default and only with automatic updates on, unless the `IdleInstall` or `InAppUpdates` policy decides), window and Quick Paste hidden, nothing unsaved, no dialog or tour, ten minutes without input in the session, and the process running for at least two minutes (`RegisterApplicationRestart` needs 60 seconds).
